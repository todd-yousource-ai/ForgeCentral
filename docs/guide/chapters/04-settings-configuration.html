Settings: Configuration and Change Control

The Forge engine keeps its settings in one governed document. Settings>Configuration shows every setting with its value, where the value comes from and how a change applies, and lets a global administrator change the ones that can change at runtime. Settings>Changes holds two-person approvals, the version history and rollback.

The engine serves the Settings tabs to global administrators only; other operators see Admin or SecurityAudit tier required. The ReadMe tab and the identity-provider list on Federation are open to every operator. A global administrator whose sign-in maps to the security-audit role can read every tab, but the engine refuses every commit, proposal, approval and rollback from that role.

The governed configuration

The governed configuration is a single document the Forge engine validates as a whole. Each commit is recorded at a version of the Forge engine's store. The store versions every other write too, so configuration versions are not consecutive. Before anything is committed (version 0), every value is the engine's fail-closed default. The settings are grouped into surfaces (for example sessions, retention, query_surface), and each row of the settings table reads like this:

  1. Setting: the setting's key, exactly as the Forge engine names it.
  2. Value: the engine's own rendering of the value in force, or not in the committed document.
  3. Source: where the value comes from. committed at version N; fail-closed default (nothing committed); node environment at boot; or compile-time constant.
  4. Applies: live, boot-bound: changes need a restart, pending: no live consumer yet, or fixed at boot.
  5. Change: Edit for a setting you can change here; read-only otherwise. Sections are edited through their forms below the table, so their rows read read-only.
  6. Definition: the engine's description of the setting and its bound (the values it accepts).

Appendix A lists every setting with its default and bound.

How a governed change works

  1. Edit a row and stage the new value. Staged changes survive switching surfaces, so one batch can span several surfaces.
  2. Commit the batch. The confirmation lists every change as key: old -> new.
  3. The Forge engine validates the whole configuration with your changes applied. It commits all of them or none.
  4. The receipt names the new version and says whether the changes applied live or which ones wait for a restart; or it lists each refused setting with the reason.
  5. Under two-person control, your commit becomes a proposal, and a different administrator approves it on the Changes tab.

Restrictions

  • Only settings the engine applies at runtime are editable here. Boot-bound settings change on the engine host and need a restart; pending settings belong to features that are not built yet.
  • A batch holds at most 64 changes; a value is at most 256 characters.
  • The six section forms each replace their whole section when committed.
  • Registering a model, and most detection and retention sections, are read-only here.

A commit does not carry the version you were looking at. If another administrator commits between your read and your commit, the later commit wins and the earlier change can be undone silently. Check Settings>Changes before committing, and coordinate changes with other administrators.

Proposals are held in the Forge engine's memory: an engine restart discards every pending proposal. There is no reject action; a proposal that should not proceed is simply not approved.

After a failed commit, Retry clears the error message but does not resend. Submit the change again.

Turning query_surface.enabled off stops the Forge engine from answering almost every ForgeCentral read, so most pages go empty. Settings stays reachable, so you can turn it back on here.

Change one or more settings

Procedure
  1. Choose Settings>Configuration.
  2. From Surface, choose the group that holds the setting.
  3. In the setting's row, choose Edit, enter the new value, and choose Stage. The row now reads Staged: and the new value, and the staged bar shows how many changes are waiting.
  4. Repeat for any other settings, on this or other surfaces.
  5. Choose Commit N changes (Propose N changes under two-person control).
  6. Read the confirmation. It lists each change as key: old -> new. Choose Commit (or Propose).
  7. Read the receipt.
    • Committed at version N. Applied live. The changes are in force.
    • Committed but not applied until a restart: followed by the keys that wait for an engine restart.
    • Proposed. A different administrator must approve it on the Changes tab.
    • Refused, followed by each refused setting and its reason (). Nothing was committed; your staged changes are kept so you can correct them.

To abandon the batch, choose Discard staged.

Change a section

Six settings are structured, so each has a form under Section settings, below the table. A form starts from the committed values and replaces the whole section when you commit it.

Procedure
  1. Choose Settings>Configuration and scroll to Section settings.
  2. Expand the section and edit its fields ().
  3. Choose the form's commit button, for example Commit egress destinations. Under two-person control the button keeps this label, but the confirmation says Propose.
  4. Confirm, then read the receipt as for a setting change.

Turn on two-person control for Settings

After this change, every Settings change is a proposal that a second administrator must approve, and the SOC response settings on Settings>SOC can no longer be changed from ForgeCentral at all. Make sure two administrators are available before you turn it on.

Procedure
  1. Choose Settings>Configuration, scroll to Section settings, and expand Dual control.
  2. Check tenant-config, and any other capabilities that should need two people.
  3. Choose Commit dual control and confirm. The version line now adds: every change here is a proposal a different Admin approves on the Changes tab.

Removing tenant-config again is itself a proposal that a second administrator approves.

Approve a proposal

Procedure
  1. Choose Settings>Changes. Pending approvals lists each proposal with its number, who proposed it, when, and which settings it changes. Proposals made on the engine host appear here too.
  2. Choose Approve on the proposal. A proposal marked Stale has no Approve: the configuration changed after it was made. It stays listed until the engine restarts; propose again.
  3. Read the confirmation, which repeats the proposer, the settings and the rule that the proposer cannot approve their own proposal, then confirm.
  4. Read the receipt: the commit receipt, or one of these refusals:
    • You proposed this change; a different Admin must approve it.
    • That proposal no longer exists (it was approved, discarded, or the node restarted).
    • The configuration changed after this was proposed, so approving it would undo that change. The proposal was discarded; propose again.

Roll back to an earlier version

A rollback restores the whole configuration as it was at an earlier version, through the same validation as any commit, and is recorded as a new version.

Procedure
  1. Choose Settings>Changes. Configuration history lists the 50 newest versions first, with the principal that committed each one and which settings changed. The current version is marked current.
  2. On the version you want, choose Roll back to N, then confirm.
  3. Read the receipt. Under two-person control, the rollback becomes a proposal with its own number.

History lists which settings changed in each version, not their old and new values. It shows the 50 newest versions; older ones exist but are not listed, and versions older than the engine's time-travel window (retention.time_travel_window_secs) drop out entirely.

A version records the committing principal as console: followed by the operator's engine principal id, not a name; an approval adds approved-by and the approver's id, a rollback adds rollback-to and the version.

Verify a change

  • On Settings>Configuration, the setting shows your new value.
  • On Settings>Changes, the newest version carries your principal id and lists the settings you changed. Its number is the version the receipt named.
  • For a change the receipt listed as waiting for a restart, the new value takes effect after the Forge engine restarts.

The version line and the Source column on Settings>Configuration show the engine store's latest version, which moves with every data write, not the version your change was committed at. Use Settings>Changes for the committed version.
