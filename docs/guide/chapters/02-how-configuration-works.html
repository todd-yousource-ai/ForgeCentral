How Configuration Works in Forge

Every setting, zone, policy and response control you change in ForgeCentral becomes an operation on the Forge engine. This chapter explains where each kind of configuration lives, how and when a change takes effect, who can make it, what is recorded, and what reaches an endpoint today. Every later chapter builds on it.

Where configuration lives

Forge keeps configuration in four places. Only the first two are changed from ForgeCentral; ForgeCentral shows the others so you can see what is in force and where it is changed.

  1. ForgeCentral is where you make every change. It sends each one to the Forge engine and shows the engine's answer; it keeps no configuration of its own.
  2. The governed configuration is the Forge engine's settings document: session lifetimes, retention windows, query limits, egress destinations, dual control, SOC response tiers and more. You change it on the Settings surface. Every commit is validated first, stored as a new numbered version, and recorded with your identity.
  3. Records are the objects you author on the other surfaces: Virtual Trust Zones, objects, policies, local users and groups, and the incidents you act on. Each has its own operation, validation and audit.
  4. Boot configuration holds the values the Forge engine reads when it starts, such as the engine's administrator assignments and its listening addresses. Settings shows them with a boot-configuration label and no edit control. They are changed on the engine host and take effect after a restart.
  5. ForgeCentral's installation settings cover sign-in (the identity provider ForgeCentral trusts), the operator role map and network ports. They are set when ForgeCentral is installed. Settings>RBAC shows the role map read-only.
  6. Forge endpoint agent settings (which sensors run on a host, how it enrolls) are set by the endpoint installer. The only configuration that travels from Forge to an endpoint is a distributed policy, which the agent pulls; see .

Re-running the ForgeCentral installer rewrites its installation settings, including the operator role map. Keep your installation inputs with your change records so a re-install reproduces them.

How a change takes effect

A change to the governed configuration goes through the same path whoever makes it:

The Applies column on Settings>Configuration tells you, for each setting, which of the three outcomes a change has:

  • Live: the change takes effect as soon as it is committed.
  • Boot-bound: the value is stored now and used after the Forge engine restarts. The commit receipt lists every committed key that needs a restart.
  • Pending: the setting belongs to a feature that is not built yet. ForgeCentral shows it read-only.

Records (zones, objects, policies, users) have no apply step: the engine resolves them each time they are read, so the next read reflects your change.

Dual control (governance.dual_control) is live for ForgeCentral: a change applies to the next commit made here. The engine host's own administration endpoint reads it when the engine starts, so there a change applies after a restart.

Who can change what

You sign in to ForgeCentral through your organization's identity provider. Your ForgeCentral role comes from the operator role map (installation settings): global administrator, tenant administrator, or tenant user.

Forge does not yet restrict governance, identity and SOC actions by role: every signed-in operator can create, publish, distribute, isolate and reconfigure identity providers. Grant ForgeCentral access only to operators who should hold those rights, and review the role map after each installation.

What is recorded

  • Settings commits, proposals, approvals and rollbacks are recorded with your identity. Settings>Changes lists every committed version, who committed it and which settings changed.
  • Zones, objects, policies, users and groups: every create, edit and delete is audited by the Forge engine.
  • Incident actions (assign, acknowledge, note, close, disposition, plan changes and approvals) are recorded on the incident's own trail, which you read on the incident's Audit Trail.
  • Log exports produce an audited receipt.

Identity-provider connector changes (configure, connect, sync, and the client secret) are not recorded, and a connector's configuration is held in memory by the Forge engine: it reverts when the engine restarts. Tenants

ForgeCentral works in the tenant of your sign-in. A global administrator works in the default tenant set in the role map. Two kinds of configuration are shared by every tenant on a Forge node: the governed configuration (Settings) and the identity-provider connector. A change to either affects every tenant.

ForgeCentral has no tenant switcher yet. To work in another tenant, sign in with an identity mapped to it.

What reaches an endpoint

Forge is advisory today. It detects activity, records it, and recommends a response; it does not block anything on an endpoint.

  • Isolate (entity drawer) records a quarantine disposition for the entity. The endpoint is not isolated.
  • An approved response plan records each step. A containment step is recorded as refused, because enforcement is off.
  • Policy distribution is the only configuration that travels from Forge to an endpoint, and it is not effective yet. See the Restrictions in .

ForgeCentral says so wherever a control could suggest otherwise: a response shows that enforcement is not active, and Isolate reports what it recorded rather than claiming the host is isolated.
